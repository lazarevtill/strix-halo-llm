New to this? Two speeds matter and they behave nothing alike. Prefill is the model reading your prompt — parallel, compute-bound, ~167 t/s here. Generation is it writing the reply — sequential, memory-bound, ~20 t/s. Paste a 44,000-token document and you wait ~4.5 minutes before the first word appears. That’s prefill, and no amount of generation tuning fixes it.

Speculative decoding — the single biggest win

A fast built-in mechanism guesses the next few tokens; the real model verifies them all in one pass. Correct guesses are free.

Depth 5 is worse than switching speculation off. Guess too far ahead and most guesses are rejected — and every rejected token still costs a full verification pass that produces nothing. “More is better” is wrong here, and the default (3) happens to be optimal.

Batch size — everyone gets this backwards

Smaller is faster, flattening below 256. -ub 256 is 29% faster than the commonly recommended 1024. -b makes no measurable difference at matched -ub. Re-running the 512 case in a separate session landed within 0.1% — this is the flag, not thermal drift.

Quantisation — the bigger file is the faster one

Speed runs backwards from file size. Generation looks memory-bound, so a smaller model “should” be faster — but unpacking the more aggressively compressed formats costs more arithmetic than the bandwidth it saves. Below roughly Q4_K you spend compute to save bandwidth you weren’t short of.

The setting swaps instruction text into the prompt rather than capping a budget — and it governs answer length more than thinking length. A 27.8B dense model needs about 2.45 PFLOP to read a 44k-token prompt, and the weight matmuls measure 10.83 TFLOPS — close to what this hardware can do. Roughly half of prefill is irreducible arithmetic. No flag, fork or kernel rewrite changes that.

Five ideas that measurement killed

Each was a sound inference from real evidence. Each took one command to disprove — and one would have cost weeks of work.

the ideawhy it sounded rightwhat happened
Rewrite the serial GPU kernelthe code really is token-by-token, and upstream fixed it for NVIDIA only1.1% of prefill
Flash attention collapses at long contexta 3.3× throughput cliff in the profilerthat data was decode, not prefill
Smaller quant is fasterdense model, memory-boundbackwards
Bigger batches are more efficientfewer, larger operations29% slower
Lower reasoning effort saves timeless thinking = fewer tokens74% slower
The habit worth copying: price the operation before you optimise it. test-backend-ops perf -o <OP> costs about a minute and needs no downtime — it refuted a multi-week plan here in one command. Finding that a kernel is inefficient proves only that the kernel is inefficient, not that it matters.
